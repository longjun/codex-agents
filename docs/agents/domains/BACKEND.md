# Backend Rules

## 适用场景

- 修改 HTTP、RPC、事件驱动服务或后台任务中的职责边界和业务编排

## 必须

- handler / controller 只处理协议输入输出、边界校验和转换，不承载大段核心业务逻辑
- service 仅在存在真实业务编排或事务边界时引入，不承担表现层职责
- repository / store 在需要隔离持久化细节、复用查询或独立测试时引入，不泄漏存储实现
- 分层必须提供明确边界；只转发参数和返回值的层应合并或省略
- 依赖方向由业务逻辑指向抽象边界，不让核心逻辑依赖传输协议或具体存储

## 建议

- 按功能组织代码，再在功能内部按职责划分
- model / entity 优先表达清晰数据和不变量；有意义的领域行为可以放在实体中
- 通用工具保持纯粹，不依赖具体业务模块
- 后台任务明确幂等性、重试、超时和退出语义

## 避免

- 为每个操作机械创建 controller、service、repository 三层
- 用全局状态传递请求数据或业务依赖
- 让 ORM、HTTP 或队列类型穿透整个业务层

## 验证

- 从入口到副作用检查一条完整路径，并覆盖关键失败和重试路径

# API Rules

## 适用场景

- 修改 HTTP、RPC、Webhook、事件消息或其他对外协议

## 必须

- 在协议边界验证并规范化输入，错误必须有稳定、明确的机器和人类语义
- HTTP 状态码、业务错误码和错误信息职责分离
- 成功与失败响应格式在同一 API 范围内保持一致
- 对外接口默认保持向后兼容，破坏性修改必须说明迁移影响
- 超时、取消、重试和幂等行为必须与操作语义匹配

## 建议

- API 只暴露调用方实际需要的数据
- 列表接口使用稳定排序和明确分页语义
- Webhook 或异步消息提供可验证来源、去重和重放策略

## 避免

- 将内部错误、堆栈、数据库结构或敏感字段直接暴露给调用方
- 用 HTTP 200 包装所有失败
- 为未来假设预留无语义字段或多套并行返回格式

## 验证

- 覆盖有效、无效、未授权、未找到、冲突和服务失败等相关边界

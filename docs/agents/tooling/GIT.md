# Git Workflow Rules

## 适用场景

- 创建或调整分支、合并、rebase、worktree、hotfix、版本标签或发布分支策略
- 普通代码提交只遵循根 `AGENTS.md` 的提交规范，不因此加载本模块

## 必须

- `main` 始终保持可验证、可发布，并作为生产发布的唯一代码来源；项目另有明确约定时从其约定
- 功能和缺陷使用从最新 `main` 创建的短期分支，完成后尽快合并并删除
- Codex 创建的分支默认使用简短的 `codex/<topic>`；生产缺陷使用 `codex/fix-<topic>`
- 生产缺陷独立于未完成功能修复：先合入 `main` 并完成必要发布，再把最新 `main` 同步回功能分支
- 合并前同步远端 `main`、解决冲突并完成受影响范围验证；不得在存在未理解冲突时继续合并
- 只从已验证的提交发布；发布后记录实际提交 SHA，项目使用版本标签时同步创建并推送标签
- 推送、合并、变基、删除分支和发布前明确目标仓库、目标分支及影响范围

## 建议

- 个人或独占分支优先 rebase 到最新 `main`，保持线性历史；已推送分支仅使用 `--force-with-lease`
- 多人共享分支优先合并 `main`，避免改写他人已使用的历史
- 可 fast-forward 时使用 `--ff-only`；需要保留审查边界时按项目约定使用 squash 或 merge commit
- 仅在任务确实并行、需要保留未提交现场或必须同时运行多个分支时使用 worktree
- 即使个人开发，也在合并前通过 PR 差异或本地 diff 完成一次自我审查
- 分支名表达领域或结果，例如 `codex/wxopen`、`codex/fix-login`，避免重复仓库和产品上下文

## 避免

- 为个人或小型项目默认引入长期 `develop`、`release`、`hotfix` 多层分支
- 从功能分支直接发布生产，或把无关缺陷修复混入大型功能提交
- 对 `main` 或共享分支执行 force push、破坏性 reset 或未经确认的历史改写
- 通过长期 stash、连续 WIP 提交或未推送的重要工作维持开发状态
- 整体 cherry-pick 已通过迁移或重组进入当前仓库的旧分支，导致重复代码和旧目录回流

## 验证

- 操作前检查工作区状态、当前分支、上游分支和目标 remote
- 提交前检查暂存差异及 whitespace；只暂存当前任务文件
- 合并前运行任务相关检查，并确认待合入提交范围符合预期
- 推送后确认本地分支与目标远端同步；发布后验证生产健康状态和实际版本
